# Lessons from earlier reviews (read before you write code)

Each rule below records a real bug the review bot found in an earlier PR, mostly while building user login (milestone 12). Your code must follow every rule that applies to it, and a test must prove it does. When a review finds a new class of bug, add a rule here in the same PR.

## Locks and races
- **Lock order is always: the user row first** (`FOR NO KEY UPDATE`, or `FOR SHARE` for a guarded insert), then the token, session, passkey or identity rows. Read a child row's `user_id` without a lock, lock the user, then re-check the child under the lock. The rule is documented in `src/store/email_tokens.rs`'s module docs.
- **Every writer of the same rows locks them in one order, on every path, counting the locks `audit::record` takes.** The order is users, then teams, then catalogs and changesets, then the `server_state` row (`bump_admin_generation`), then the rest (a `server_settings` row). Among users it is `users::set_admin`'s and `users::delete`'s: every admin by id, then the others by id. `record` locks users `FOR KEY SHARE` in the middle of your transaction (through `audit_person`, `audit_credential` and `audit_team_ref`): the actor, its credential's owner, the entry's person and a personal team's person. So every store function that records calls `audit::lock_people(&mut tx, actor, &People { target, users, teams, catalogs })` first, naming every user, team and catalog its entry will resolve; it sorts them, then takes each in that order, using the target's requested lock mode and `FOR KEY SHARE` for the rest. Bugs this prevents, all found in review: settings `reset` deleted its row before bumping, which deadlocked against `set`, and both bumped before `record` locked the admin actor, which deadlocked against `set_admin` (PR #416); team and catalog writers recorded a personal team's person or the actor after locking the team or catalog, which deadlocked against the user's deletion, and an actor locked before a lower-id admin deadlocked against `set_admin` (issue #397). When you add a writer, check its order against every other writer of those rows, including a path that ends up writing nothing. Test the pair with the interleaving forced: hold a row one side needs midway (`FOR UPDATE`), queue the change, watch `pg_stat_activity`, take the other side's next lock under a timeout, then release.
- **Audit rows are part of the lock order too; refreshing an existing reference must not wait on its audit row.** `audit_person`, `audit_team_ref` and `audit_credential` used to upsert their row on every call; `ON CONFLICT DO UPDATE` locks the existing row even when nothing changes, so admin A inviting B while B invited A (or acting on each other's personal teams through `team_ref`) each held one `audit_people` row and waited for the other's, a deadlock that ordering the `users` rows did not prevent (found in review of PR #419). Since migration `0014_audit_row_locks.sql` a resolver reads an existing row without a lock and refreshes a stale one only under `FOR NO KEY UPDATE SKIP LOCKED`; every user and team gets its row in the transaction that creates it. Never add a SQL function or statement that upserts or updates a shared audit row unconditionally; if a new audit table needs one, give it the same read-first, skip-locked shape. Test it with two actors acting on each other while a third transaction holds one of the rows: both must finish under a timeout.
- **A credential change and its consequences go in one transaction.** Redeeming a link, setting a password or passkey, and revoking sessions all commit together. Hash before you open the transaction, never inside it.
- **Every session insert is guarded against a concurrent credential change.** A password sign-in uses the stamped path (`passwords::Verified { stamp }`, then `user_sessions::start` with `password: Some(stamp)`). Other methods must not create a session that survives a reset or admin change. Ask: if a reset or `set_admin` commits between my check and my insert, does the session still appear? If so, fix it. Test that interleaving deterministically: hold the user row, queue both operations, and watch `pg_stat_activity`.
- **After a commit, await nothing that can block or fail before returning the response:** record success events in the transaction; side effects are in-transaction or detached best-effort.
- **Maps keyed by a client-chosen value** (IP, email, ceremony id) use `ExpiringMap::update_or_insert_sliding` (find-or-create plus change under one lock), never `get` followed by `insert`.
- **Admin level and ceiling come from the key cache on every request**, never from a value read at sign-in.

- **Every race test that holds a lock or waits on another task has a timeout** (`tokio::time::timeout`, about 30 s) and fails with a message naming what it waited for. A hung test once stalled a task for 12 hours. Run gates through `tools/agentic/gate.sh`, which enforces a hard timeout. Release held locks on every path, including assertion failures (use a guard or drop the connection).

## Inputs and errors
- **Normalize user text before it reaches SQL.** Postgres rejects NUL, so a NUL becomes a 500. Use `users::normalize_email` and `users::is_lookup_email`. A malformed value must take the same path as "unknown", with the same status, the same body and the same cost.
- **Every refused sign-in looks identical:** the same 401 text, one argon2 check, and no hint whether the account exists.
- **Genuine database errors stay 500.** Don't turn them into 4xx.
- **Bounded state per actor.** When any client, signed in or not, can add entries to a shared in-memory map (flows, ceremonies, pending authorizations), limit each actor: by address for anonymous starts, by user or session for signed-in ones. A new entry from the same browser or session must replace its previous one instead of stranding it. Test that one actor's repeated starts never grow the map and that others can still start.
- **A test that a JSON field is `null` checks the key is there:** `assert_eq!(body.get("notice"), Some(&serde_json::Value::Null))`, never `body["notice"] == Null`. serde_json's `[]` answers `Null` for a missing key, so the weaker form passes when the field is dropped (found while revert-checking issue #364).

## Browser-facing pages and routes
- **Every state-changing form POST on a server-rendered page** must call the cross-site check in `src/http/signin.rs` (`Sec-Fetch-Site` must be `same-origin` or `none`). This blocks login CSRF. Don't use `Origin`: with `Referrer-Policy: no-referrer`, browsers send `Origin: null`.
- **Cookie-authenticated `/api/v1` writes need `X-OKF-CSRF`.** In the console JS, every request, including raw fetch and XHR uploads, builds its headers through `authHeaders` in `core/api.js`.
- **`return_to` goes through `pages::safe_return_to`.** Test hostile values: `//evil.example`, `https://evil.example`, `/\evil.example`, `javascript:`, and their encoded forms.
- **Request traces log the path only.** Never put a secret in a URL's query if you can avoid it. When it can't be avoided (emailed links), it must still never be logged.
- **No secret reaches a log line or `Debug`:** passwords, tokens, session ids, CSRF tokens, WebAuthn or OIDC state, verifiers, nonces. Give such types a hand-written `Debug`.

## Console behaviour
- **The console uses one credential at a time:** a live cookie session wins over a stored key.
- **Sign-out counts as done only on a 2xx, or a 401** meaning the session was already over. Any other failure keeps the session and shows a retryable error.
- **A browser journey for a write path** must actually perform the write and check the persisted result. It must fail if the header or feature it covers is removed; check that by temporarily reverting the code.
- **Every console control that starts a write is disabled until the write settles, tracked by a stable key, not on the element.** A table re-sort, a list Refresh or a reopened drawer draws a new, enabled button, so a disabled flag on the old one does not stop a second request. Mark controls with `guard(el, key, allowed)` and start writes with `once(key, write)` from `core/pending.js`. Test it by holding the request (`Ui::hold_next`), clicking (`Ui::click_twice`), redrawing (`Ui::mark`, then a sort or Refresh, then `Ui::wait_redrawn`), clicking again, and checking `Ui::held_matches` is 1.
- **A refusal's reason must show even when the read after it fails.** Redraw from the last answer, marked as possibly out of date, and leave every control usable; never let the refresh's success decide whether the reason or the controls come back. Test it with `Ui::fail_next` on the follow-up GET.
- **Overlapping reads draw only the newest answer, and a settled write updates the view that shows its object now.** Number each list or drawer load and drop an answer a newer load has overtaken (a Refresh racing an action's reload). When a write settles, re-render whichever drawer shows the written object now, through that drawer's own ticket, not the drawer the write started in, which may have been closed and reopened. Test with `Ui::hold_answer` (a late answer) and `Ui::hold_next` across a close and reopen. **Take the redraw's number as the write settles, before any other await** (the list refresh): numbered only when the redraw starts, an older write whose list read answered late took the newest number and drew its saved answer over a newer write (found in review of PR #384). Test it by holding the first write's list read (`Ui::hold_answer`) across a newer write. **Scope that number to the drawer or object the write updates:** a page-wide counter bumped by a write of team A cancelled the pending read of team B's drawer, which then never opened. Bump it only while the drawer shows the written object (or number per ticket), and test a write of one object settling while another's drawer is loading.
- **A failed side read never discards a write's answer, or another read that succeeded.** When a drawer redraws after a write from the write's answer plus another read (the users for a picker), settle each part on its own (`Promise.allSettled`, or a fallback to the previous value), draw the answer, and mark only the failed part as possibly out of date. `Promise.all` rejects as a whole, so a failed users read once threw away a committed suspension and redrew the team as active. Test it with `Ui::fail_next` on the side read after a successful write (found in review of PR #384).
- **A journey that checks a message the page shows by toggling `hidden`** waits for it to be visible (`ui.wait_visible`), not only for its text: `ui.wait_text` reads `textContent`, which a hidden element still has, so the check passes even when the message never shows (found while revert-checking issue #326).

## Process
- **Find the whole class.** When you fix one path, grep for every sibling path with the same pattern and fix those too.
- **Tests must fail without the fix.** Verify that by temporarily reverting the code, and say so in your report. After restoring a reverted file, `touch` it (or restore with `git checkout`, which sets a new modification time). Otherwise cargo can reuse the test binary built from the reverted copy and report stale results.
- **The PR description and claims must match the final code** exactly. Update them after every review round.
