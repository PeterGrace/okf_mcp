# M12 Task 9: OIDC sign-in and linking

## Added
- `[[auth.oidc]]` providers (id, label, issuer, client_id, client_secret_env, scopes); the secret is read from the environment at start-up, and a missing one fails start-up. Unknown keys (an inline `client_secret`) are refused when the file is parsed.
- `src/oidc.rs`: `OidcProviders`, with discovery cached for an hour (a failed refresh keeps the cached document and retries after a minute), the authorize URL (PKCE S256, state, nonce), the code exchange and ID-token verification (issuer, audience, expiry, signature, nonce), and a reqwest 0.13 adapter with redirects off. An in-process mock provider for tests.
- `/auth/oidc/{provider}/start` and `/callback`: the flow lives on the server under a random id held in a ten-minute `SameSite=Lax` cookie, is single use, and the app compares `state` itself in constant time. Sign-in finds the user by `(provider, sub)`, else links by a verified email (string booleans accepted) with a notice mail, else 403.
- `POST /api/v1/me/identities/{provider}/link` (session and CSRF header): a signed-in user links an account whatever its email; the callback links only for the browser still holding that live session, and ends the user's other sessions unless `keep_sessions`, in one transaction.
- `store::identities` (find, link, sign_in, link_for_session, touch, list, unlink) and `store::sign_in_methods::count`.
- One button per provider on `/signin`.

## Changed
- An OIDC sign-in is one transaction (`identities::sign_in`): the user's row, the link (re-read or made), the browser's old session, the new session, `last_used_at` and the `sign_in_events` row, then the commit. After a sign-in or link commits, nothing that can block or fail runs: the method-added notice is queued on a detached task. `sign_in_events::record_in` and `Attempt`, `user_sessions::start`/`revoke` over an executor, `hold_live` and `console_session::session_cookie` match Task 8's.
- `http::signin::message_page` is shared with the OIDC callback.

## Notes
- Every link and unlink locks the user's row first (`FOR NO KEY UPDATE`), per the lock order in `email_tokens`' module docs; only `identities::touch` (the `last_used_at` stamp) takes no user lock.
- A `sub` that is empty, over 255 bytes or holds a control character is a refused ID token (400), and an email Postgres would refuse is stored as no email: hostile token text is never a database error.
- Each sign-in start takes from the per-address sign-in limit (a burst of 30, refilled one per 30 seconds), so one address cannot fill the flow map. A new start drops the flow its browser held before. A link start replaces the previous link flow of its session and takes from a per-user allowance (a burst of 10, refilled one per minute), so a signed-in user cannot fill the map either (PR #341 review).
- A user links at most one account per provider.
