# M8 Task 1: error payloads write `/`-prefixed catalog paths (2026-11-04T00:10:15Z)

Issue #160, Task 1 of `docs/superpowers/plans/2026-11-03-okf-mcp-m8-changeset-handles.md`
(Decision 9). The things-to-fix follow-up from the review of PR #152.

## Added

- `src/error.rs`: `client_path` (adds the leading `/` unless it is there) and
  `findings_json` (a `LintFailed` finding list with each `file` prefixed).
- Tests: `to_json_writes_catalog_paths_with_a_leading_slash`,
  `lint_failed_findings_name_their_file_with_a_leading_slash` and
  `invalid_path_is_prefixed_unless_it_leaves_the_catalog`.

## Changed

- `OkfError::to_json` writes `path` `/`-prefixed for `NotFound`,
  `FrontmatterParse`, `Shape`, `SecretDetected` and `EditMismatch`, and each
  `errors[].file` and `warnings[].file` of `LintFailed`.
- `InvalidPath`'s `path` is prefixed too, unless it is empty or climbs out of
  the catalog once normalized (`escapes_root(&normpath(path))`: `..`, `../x`,
  `infra/../../x.md`), which is echoed as given.
- The doc comments of those fields, of `to_json` and of `Finding::file` say
  the payload adds the `/`.
- README ("Tools") and the design's "Errors" section state the rule, and that
  report results keep `okf.py`'s unprefixed paths.
- Existing `src/error.rs` tests for `SecretDetected`, `EditMismatch` and
  `LintFailed` expect the slash.

## Notes

- Unchanged: the messages (`to_string`), the variants' internal values,
  `Io`'s `path` (it can be a filesystem path or an archive entry's name),
  `Config` (its payload has no `path`), `Conflict` and `StillLinked` (already
  prefixed), and the report results (`lint`, `oldest`, `sprawl`,
  `links_report`), which the `okf.py` parity tests pin. So the same lint
  finding is `/a.md` in a `LintFailed` error and `a.md` in `lint`'s result.
- No test outside `src/error.rs` asserted an unprefixed error-payload path;
  the plan's Task 1 records that.
