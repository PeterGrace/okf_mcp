# M5: writes (2026-11-03T11:41:02Z)

Milestone 5 of the OKF MCP server (design:
`docs/superpowers/specs/2026-10-26-okf-mcp-server-design.md`; plan:
`docs/superpowers/plans/2026-11-03-okf-mcp-m5-writes.md`; epic #89). Agents can now
change a catalog through the server:

- each connection's edits go to a changeset per (catalog, key, label), held in
  Postgres, and survive disconnects and restarts until published or discarded;
- reads through that connection see its pending edits (an overlay);
- the content write tools (`create_concept`, `edit_document`, `replace_body`,
  `set_frontmatter`) and the bookkeeping tools (`stamp`, `review`, `question`,
  `unquestion`, `add_source`, `log`, `index`), ported from `okf.py` byte for byte;
- `publish` with base-revision conflicts, replay of `log.md` and `index.md`
  bookkeeping onto newer text, the write rules and lint;
- `discard`, `revert`, `pending_changes`, `stranded_sessions`, `adopt_changeset` and
  `lint pending`;
- each MCP session bound to the key that opened it.

Moving, splitting and deleting concepts are M6.

## Decisions

All seven were decided by Claude; pgrace delegated every open question of the
milestone (2026-11-03).

1. **Changeset identity is (catalog, key, label).** The label is the connection's
   `X-OKF-Changeset` header, else `?changeset=` on the MCP URL, else `default`; never
   the MCP session id, which would strand an unlabelled client's edits on every
   reconnect. Migration `0002_changeset_identity.sql` renames `session_id` to `label`,
   makes the open-changeset unique index `(catalog_id, key_id, label)` and adds a
   `version` counter.
2. **An MCP session is bound to the key that opened it** (`http::sessions`); another
   key naming it gets 404, rmcp's answer for an unknown session.
3. **Writes take the catalog row first** (`FOR KEY SHARE`), then the changeset row;
   `catalogs::delete` takes the row `FOR UPDATE` first, so neither deadlocks the other.
   `40P01` and `40001` map to `OkfError::Busy`.
4. **`install/`, the root `docs/` and the root `tests/` are read-only machinery** for
   every write tool, `revert` included.
5. **No derived-column backfill in M5**: `Derived::of` is unchanged.
6. **Overlays are rebuilt whole and cached** per changeset while its `version` and the
   base snapshot's `generation` are unchanged; a write rebuilds under the row lock
   (kept after Task 13's measurement).
7. **The bookkeeping ops are checked byte for byte against `okf.py`** (the parity
   shim's `ops` command, `tests/golden/ops.json` and a live test).

## Deviations from the design

From the plan's "Simplifications and deviations relative to the design", all written
into the design's "What M5 shipped differently":

- changesets per (catalog, key, label), not per (MCP session, catalog);
- no discard when an MCP session closes (rmcp 3.8 has no close hook); the 24-hour prune
  of empty changesets stays;
- `stranded_sessions` lists changesets idle past `session_idle_timeout`;
- `OkfError` gains `Busy`, beside `SecretDetected`, `EditMismatch`, `LintFailed` and
  `Conflict`;
- `publish` with nothing to publish returns `published: false`;
- `LintFailed` is 422; publish records the publishing key's actor; a file whose result
  equals the published one gets no revision; links into deleted paths are
  `link-into-deleted` errors in `LintFailed`.

## Follow-ups

None filed as issues; listed here for M6 and later.

For M6:

- `move_concept`, `split_concept` and `delete_concept` on `write::apply`. A deletion
  is a touched path the op removed (through `MemWorkspace::remove`), stored as a
  deletion entry only if the path is published. Their listing changes need
  `ReplayOp` variants for renaming and removing an index bullet.
- The derived-column backfill (an `okf-mcp reindex` subcommand), with the first change
  to `Derived::of` (Decision 5).

Accepted or left as they are in M5:

- **Pool connections** (Tasks 8 and 10): each write holds one pooled connection for its
  whole transaction, so writers queued on one changeset's row lock each hold one
  while they wait, and enough of them can leave reads waiting on the 8-connection
  pool; a publish holds one and needs a second to refresh a stale snapshot, so many
  catalogs publishing at once could exhaust the pool until the acquire timeout fails a
  publish. Accepted for now; a larger pool or a per-changeset queue would address it.
- **`write::apply`'s `Busy` branch for a closed changeset has no test** and no known
  way to reach it (Task 10: a write queued behind a publish or discard opens a new
  changeset in `get_or_create`). It stays as a defensive check; its doc says so.
- **`create_concept`'s `parse_checked` guard has no test** (Task 4 review): a probe
  found no input the renderers write unparseably.
- **The overlay cache has no size cap** (Task 7 review, deferred): entries are dropped
  when idle or outdated, not by count.
- **One `find_open` per selected catalog** for write and admin keys on every read, and
  **duplicate concurrent first builds of one overlay** (Task 7 review): left as they
  are.

From the plan's "Deliberately deferred" table, unchanged:

- `move_concept`, `split_concept`, `delete_concept` (M6);
- discarding a changeset when its MCP session closes (M7, or never: rmcp 3.8 exposes
  no per-session close hook, and changesets outlive sessions on purpose);
- a backfill of derived columns when `Derived::of` changes (when it changes);
- the NTP check, `time_server`, TLS to Postgres and deployment (M7);
- more than one replica (never).

Known, not filed (from M4, still true):

- **testcontainers leaks a container on `StartupTimeout`.** One
  `postgres:17-alpine` testcontainer, about 8 hours old and not started by this task,
