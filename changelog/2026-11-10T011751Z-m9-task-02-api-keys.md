# M9 Task 2: API keys

Issue #217, Task 2 of `docs/superpowers/plans/2026-11-09-okf-mcp-m9-web-console.md`.

## Added

- `/api/v1/keys` (`src/http/api/keys.rs`), six admin-only endpoints that call
  the same `store::keys` functions as `okf-mcp key ...`:
  - `GET /keys`: the keys the caller manages, revoked ones included, never a
    secret or a hash (`KeyView` is built by destructuring `KeyRecord` and
    dropping `sha256`);
  - `POST /keys`: creates a key and answers `{key, secret}`, the only response
    holding a secret (`CreatedKeyView`'s `Debug` redacts it); `actor` defaults
    to the name, as in the CLI;
  - `PATCH /keys/{id}` (the maintenance-report flag), `POST /keys/{id}/revoke`,
    `PUT` and `DELETE /keys/{id}/catalogs/{catalog}` (grant and ungrant).
  Each change reloads the key cache at once, so it takes effect on the next
  request.
- The API keys page (`src/http/ui/js/pages/keys.js`): the managed keys with a
  "show revoked" filter, a create form in the drawer, a modal that shows the new
  secret once (copy button; Escape does not close it, and the secret is removed
  from the page when it is dismissed), and per-key grant, ungrant, reporting and
  revoke, with a warning when revoking the signed-in key. Its styles are
  appended to `styles.css`.
- Seven API tests (the access matrix, the secret shown once, the default actor,
  reach on create, reach on grant and ungrant, reporting and revoke taking
  effect at once, a legacy id changing only its own key) and a store test of a legacy key
  rotated between lookup and change and three browser journeys (`tests/ui_e2e/keys.rs`): create a
  key and sign in with its secret, revoke the signed-in key and land on the
  login card, and a read key never seeing the page.
- `docs/operations.md` "Web console" gains an "API keys" subsection with the
  endpoint table and an example; `README.md` mentions the page.

## Changed

- `store::keys` gains `*_by_id` forms of its four key changes, sharing their
  bodies with the `*_target` forms the CLI keeps using.
- `api::require_admin` and the harness's `Ui::wait_hidden` lose their
  `#[allow(dead_code)]`: this task is their first caller.

## Notes

- A catalog-scoped admin manages only keys that are not all-catalogs keys and
  whose every catalog it reaches; any other key is 404, like an unknown id. A
  new key or grant may name only catalogs the caller reaches (404 otherwise),
  and `all: true` needs a caller reaching every catalog (403). A key with no
  grants left reaches nothing and is managed by every admin.
- Paths take key ids only. The handler finds the record by exact id among the
  managed keys and changes it through new `store::keys` functions
  (`revoke_by_id`, `set_maintenance_report_by_id`, `grant_by_id`,
  `ungrant_by_id`). They lock exactly that row in the change's transaction and
  never resolve a name. The CLI's `*_target` functions resolve a legacy id (a
  row from before migration 0005, whose id is its name) by active name, so
  with them a change could reach another key of that name, including a
  replacement created between the reach check and the change (review of
  PR #226).
- Key changes record no audit actor (`store::keys` has none), as with the CLI.
- The name cell is `white-space: nowrap`: wrapped, its centre fell between the
  two lines on the bare cell and the journey's click was refused. The plan
  records this, and that `.drawer-actions` stays in Task 1's block only.
