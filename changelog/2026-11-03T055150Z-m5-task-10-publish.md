## Notes

- **Lock order:** the in-process mutex, then the advisory lock (`store::catalogs::lock`, the one import takes), then the catalog row (`FOR KEY SHARE`), then the changeset row (`FOR UPDATE`). The mutex is held through the snapshot refresh after commit, so the next publish checks against this one's result.
- **Why 422 for `LintFailed`:** the request is well formed. What fails is the catalog state it would produce, and the fix is to edit documents, not the call. 409 stays for `Conflict`, where the state moved under the request.
- **Why the content rules run on every changed file:** replayed text is new, and an entry may have been stored before a rule existed.
- **Which lint findings refuse:**
  - errors in changed files refuse;
  - so do links from unchanged documents into deleted paths (`link-into-deleted`);
  - errors elsewhere and warnings in changed files come back as `warnings`;
  - warnings elsewhere are left out.
- **No revision for an unchanged result:** a path whose result equals the published file gets no revision. If nothing was written, the generation does not move.
- **A deletion entry is never replayed.** A deletion with no base revision names a path published after the changeset's first edit, so it is a `Conflict`.
- **The unique-violation backstop:** a unique violation while writing becomes `Conflict`, never the opaque `Database` error.
- **A write queued behind a publish is not `Busy`.** The write waits in `get_or_create`'s `SELECT ... FOR UPDATE`. Once the publish commits, Postgres re-checks `state = 'open'` and finds no open changeset, so the write opens a new changeset and keeps its edit. `write::apply`'s `Busy` branch stays as a defensive check. The Task 8 note assumed the queued write would get `Busy`; the test pins the real behaviour.
