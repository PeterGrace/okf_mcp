# M4 Task 4: `app`: the shared state and the poll loop (2026-11-03T00:20:19Z)

Issue #68, Task 4 of `docs/superpowers/plans/2026-11-02-okf-mcp-m4-read-only-server.md`
(milestone 4, epic #64).

## Added

- `src/app.rs`:
  - `App`: the pool, the configuration, the clock (`Arc<dyn Clock>`), the key cache
    (`Arc<Keys>`) and every loaded catalog (`Catalogs`, a `BTreeMap` by name behind a
    `std::sync::RwLock<Arc<_>>`, swapped whole), with accessors `pool`, `config`,
    `clock`, `keys`, `catalogs` and `catalog`.
  - `App::load`: reads `admin_generation` before the keys (so a change committed
    between the two triggers a reload at the next poll), loads every live key and every
    catalog. A catalog that fails to load is logged and left out; a catalog deleted
    between the list and the load is skipped quietly. A missing `default_catalog` is a
    warning, not an error.
  - `App::poll`: one pass of design "Noticing changes made outside the server". A
    moved `admin_generation` reloads the keys; a failed reload, or a failed read of the
    counter, is logged, leaves the counter unstored (so the next pass retries) and does
    not stop the pass. The catalog list adds new catalogs, drops deleted ones, loads a
    catalog re-created under the same name (a new id) from scratch, and refreshes, in
    place, any whose `generation` moved. A catalog that fails to load is logged and
    skipped; a failed refresh keeps the old snapshot. A catalog whose stored data would
    not build is remembered with that generation (inside the `polling` mutex) and tried
    again only once its generation moves; a database error is retried at the next pass. A
    catalog deleted between the list and its load or refresh is skipped with a debug
    line, not an error.
  - `App::poll_until`: runs `poll` every `poll_interval` (`MissedTickBehavior::Delay`)
    until a `CancellationToken` is cancelled; a failed pass is logged.
  - Ten tests (Postgres): `load_holds_every_catalog_and_live_key`,
    `poll_notices_imports_new_and_deleted_catalogs_and_revoked_keys`,
    `overlapping_polls_leave_the_newest_key_list`,
    `poll_reloads_a_catalog_created_again_under_the_same_name`,
    `a_catalog_that_fails_to_load_is_skipped_until_it_changes`,
    `a_failed_refresh_keeps_the_old_snapshot_until_the_catalog_changes`,
    `a_re_created_catalog_that_fails_to_load_drops_the_old_one`,
    `a_failed_admin_generation_read_does_not_stop_the_pass`,
    `a_failed_key_reload_does_not_stop_the_pass_and_is_retried`,
    `poll_until_stops_when_cancelled`. Plus `only_data_failures_are_remembered_as_broken`
    (no database).
- `src/catalog.rs`: `CatalogState::description`, `Loaded::files` (every stored live
  file, markdown or not) and `Loaded::last_change` (the newest `updated_at`, `None`
  for an empty catalog), for `list_catalogs` (Task 5); test
  `load_records_the_description_file_count_and_last_change`.
- Dependency `tokio-util` 0.7.20 (`CancellationToken`, the type rmcp's config takes).

## Notes

- The catalog list is read every tick, so a new, deleted or re-created catalog appears
  whether or not `admin_generation` moved: two small queries per tick.
- Passes are serialized by `polling` (a tokio `Mutex`, held across `.await`s), so a
  direct `poll` beside the loop cannot swap an older key list in after a newer one.
- A refreshed catalog keeps its `Arc<CatalogState>`: a reader holding it sees the new
  snapshot; only a re-created catalog gets a new state.
- Remembering broken generations (review of PR #79): without it, a catalog whose data
  stays broken was read, rebuilt and logged as an error every `poll_interval`. The
  cost is that a repair made in SQL without moving the generation goes unnoticed until
  the next import or publish; the subcommands always move it.
- A re-created catalog whose load fails is missing until it loads: the old content no
  longer exists to serve.
- Cancellation is noticed between passes; a pass in progress finishes first.
- Nothing logs a key or `DATABASE_URL`: the log lines name the catalog and the error.
