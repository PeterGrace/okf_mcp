# M5 Task 7: overlays, and the read tools through them (2026-11-03T043535Z)

Task 7 of `docs/superpowers/plans/2026-11-03-okf-mcp-m5-writes.md` (milestone 5), issue #96.

## Added

- `Loaded::{workspace, revision}`. `catalog::build` used to drop the `MemWorkspace` it
  built the snapshot from; `Loaded` now keeps it (each file's bytes are held once more,
  about 450 KB for the real catalog) and each live path's revision (a new changeset
  entry's base, for Task 8).
- `MemWorkspace::with_changes(changes)`: a copy with writes (`Some`) and deletes
  (`None`) applied, checked as `from_stored` checks its input (an escaping path or a
  file that is also a directory is `InvalidPath`). The original is unchanged. Task 8
  copies an overlay with `with_changes(std::iter::empty())`.
- `CommitTimes::with_dirty(dirty)`: the same commit times with more paths marked
  uncommitted (`CommitTimes`' maps are private, so a `Loaded`'s record cannot be rebuilt
  with `new`).
- `src/overlay.rs` (Decision 6):
  - `Overlay`: the base `Arc<Loaded>`, the changeset id and `version`, the overlaid
    workspace, a full `Snapshot::build` of it, the dirty paths, and the base's commit
    times with those paths marked uncommitted. Accessors `snapshot`, `workspace`,
    `base`, `dirty`, `changeset_id`, `version`, and `lint(now)`.
  - `build_overlay(base, changeset, entries)`, on a blocking thread; a `content: None`
    entry deletes its path.
  - `Overlays::new(idle)`, with `get(pool, state, changeset)` and `forget(id)`. A cached
    overlay is reused while both the changeset's `version` and the base's `generation`
    are unchanged. Storing one first drops every entry unused for `idle`
    (`session_idle_timeout`), and never replaces a newer build of the same changeset
    with an older one (a slower build finishing last). No incremental snapshot.
  - `View::{Published, Pending}` with `snapshot`, `lint(now)` and `pending`.
- `App::overlays`, built from `session_idle_timeout`.
- `ToolContext::view(state)`: this key and label's overlay if they have an open
  changeset in the catalog (one `find_open` lookup on the open-changeset index), else
  the published state. A `read` key returns `Published` without a query: it can never
  hold a changeset, so plain readers pay nothing.
- `mcp::reports::LintParams { catalog, pending }`, and `Lint::pending`.
- `mcp::testing::app_at(catalogs, config, imported, clock)`; `app_with` delegates to it
  with now and the system clock.
- Tests: `with_changes_copies_the_files_and_applies_writes_and_deletes`,
  `with_dirty_marks_more_paths_uncommitted_and_leaves_the_original`,
  `loaded_keeps_the_workspace_and_each_path_s_revision`,
  `an_overlay_shows_the_entries_over_the_published_files`,
  `the_cache_is_reused_until_the_version_or_the_generation_moves`,
  `the_view_is_pending_only_for_the_key_and_label_with_an_open_changeset`,
  `get_concept_sees_a_pending_edit_only_on_the_key_and_label_that_made_it`,
  `pending_lint_counts_the_changeset_s_paths_as_uncommitted`.

## Changed

- `search`, `get_concept`, `read_document`, `open_questions`, `oldest`, `sprawl` and
  `links_report` read through `ctx.view`, so an agent sees its own pending edits and
  nobody else's. `get_concept` and `read_document` are now `async`.
- `lint` takes `LintParams`. Without `pending` it lints the published catalog, as
  before; with `pending: true` it lints the connection's view, the changeset's paths
  counted as uncommitted for `generated-after-commit`. `Lint::pending` says which ran
  (`false` when `pending` was asked for but there is no open changeset).
- Design: "In-memory snapshot" (the overlay paragraph), "Crate layout" (an `overlay`
  row), "Read tools" (the `lint` row and the commit-time paragraph) and "Data flow",
  "Read", step 4.
- Plan: a dated Corrected note in Task 7, and the File map no longer lists
  `src/mcp/history.rs` for Task 7.
