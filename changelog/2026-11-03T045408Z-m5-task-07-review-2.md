# M5 Task 7: second review of PR #111 (2026-11-03T045408Z)

Answers Brooke's second review of PR #111 (issue #96). The coordinator decided the design.

## Changed

- **`search` skips a catalog whose view fails.** Before, one connection's broken overlay
  failed its whole multi-catalog search.
  - A catalog whose `ToolContext::view` fails is left out and listed in the new
    `SearchResult::skipped: Vec<SkippedCatalog { catalog, error }>`, where `error` is
    `OkfError::to_json()` (internal errors masked as usual).
  - Every other catalog still answers.
  - A skip is logged at `warn` with the catalog and error kind only.
  - The tool description says so.
- **Single-catalog reads keep the error.** `get_concept`, `read_document` and the reports
  don't fall back to the published state, which would silently hide the agent's own
  pending edits.
- **The overlay error says how to recover:** `<path>: is a file and a directory, in
  pending changeset N; discard the clashing path (<path> or the paths under it) or the
  changeset`.
- **A comment in `Overlays::get`** explains that entries read after `find_open` may be
  newer than the version the overlay is labelled with, and why that is harmless.
- **Design, "In-memory snapshot":**
  - each cached overlay pins a workspace copy, a snapshot and its base, so memory is
    about N active changesets times the catalog's size, bounded by the idle eviction;
  - a broken overlay errors rather than falling back, and `search` skips it.
- **Design, "Read tools":** the `search` row mentions `skipped`.
- **Plan:** Task 7's Corrected note records the decision.
- **New tests:**
  - `a_catalog_whose_overlay_fails_is_skipped_and_the_others_answer`;
  - `a_broken_overlay_is_reported_not_hidden_behind_the_published_state`.
  - `a_clashing_entry_names_the_pending_changeset` now checks the recovery wording.
