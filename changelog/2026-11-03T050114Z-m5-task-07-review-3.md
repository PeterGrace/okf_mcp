# M5 Task 7: third review of PR #111 (2026-11-03T050114Z)

Answers Brooke's third review of PR #111 (issue #96). The coordinator decided the fixes.

## Changed

- **`mcp::context::is_broken_overlay(error)`** is new. It holds for a `ToolContext::view`
  error that is neither internal nor `Busy`, that is, the overlay failing to apply.
- **`search` skips a catalog only for a broken overlay.**
  - A `Database` or `Busy` error from `view` now fails the call, so the agent retries.
    Before, it showed up as a successful search with fewer hits.
  - `tool_error` logs an internal error at `error` with `%error`, as before.
  - A skipped error is never internal, so its `warn` log keeps the catalog and kind.
- **`get_concept` and `read_document` look past a broken overlay.**
  - A broken overlay in one catalog of the read set no longer hides a later catalog
    that resolves the path.
  - The first broken overlay's error is kept, through the new private helper
    `view_or_note`.
  - If no catalog resolves the path, that error is returned, not `NotFound`.
  - Database and `Busy` errors still fail the call at once.
- **Design, "In-memory snapshot":** says how each read tool treats a broken overlay, and
  that a cap on the number of cached overlays is deferred.
- **Plan:**
  - Task 7's Corrected note records these rules;
  - Task 8's facts note says `apply` never uses `overlay.version()` as a concurrency
    token: it re-locks the changeset row and takes the overlay under that lock.
- **New tests:**
  - `a_database_failure_fails_the_search_instead_of_skipping`;
  - `a_broken_overlay_in_one_catalog_does_not_hide_a_later_catalog`.
