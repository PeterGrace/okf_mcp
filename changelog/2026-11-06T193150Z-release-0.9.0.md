# Release 0.9.0: credential names and rotation

Prepared at 2026-11-06T19:32:55Z. Includes PR #176 (issue #174).

## Changes

- Group API credentials by name, with one live credential per name/actor
  pair. Different actors can share a name, and revoked pairs can be reissued.
- Give new credentials immutable UUID IDs while preserving existing IDs,
  secrets, grants, and historical changeset ownership.
- Select credentials for revoke/grant/ungrant by generated ID, unambiguous
  live name, or `NAME --actor ACTOR`. Ambiguous names are refused with IDs.
- Report revoked names explicitly when no live replacement matches.
- Add check-only `just fmt`, `just lint` (clippy and rustdoc), and `just test`.

## Compatibility

- `key list` is tab-separated in this order: **name, actor, id, access,
  state, catalogs, default**. Update scripts that parse the old columns.
- MCP `list_changesets.key` is an opaque credential ID (a UUID for new keys);
  display `key_name` for its human grouping name.
- Pre-0005 IDs equal their names and use live-name resolution. Select with
  `--actor` when the name is shared; after rotation, that name selects its
  live replacement. New generated IDs retain exact-ID precedence.
- Existing secrets continue to authenticate. IDs identify credentials;
  they are not authentication secrets.

## Production upgrade

After merging this release preparation, push `v0.9.0` at the merged commit.
The image workflow publishes `ghcr.io/petergrace/okf-mcp:0.9.0`; wait for a
successful build before changing the production Deployment's image.

Before rollout, take and verify a database backup. Startup applies migration
`0005_key_names.sql`, which adds and backfills names and enforces one live
name/actor pair. With the Deployment's `Recreate` strategy, the old pod stops
before the new pod migrates and starts. Verify readiness, version, migration
completion, catalog access, and key listing after rollout. MCP clients
reconnect; persisted changesets survive.

Migrations are forward-only: after 0005, the 0.8.0 binary refuses the newer
schema. Rollback requires restoring the pre-upgrade backup, or fixing forward
with a new release. See [the operations guide](../docs/operations.md#8-upgrades).
