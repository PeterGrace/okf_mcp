# Remove a `sources` entry (`remove_source`)

Issue #192. No tool removed an entry from a concept's `sources`:
`add_source` appends one, `set_frontmatter` refuses the key, and `okf.py`
had no such command either. Cleanup used to mean editing YAML in a git
checkout, which stopped being possible once the server became the source of
truth, so a `split_concept` that left unused sources on the hub or the new
concept had no fix.

## Added

- `ops::remove_source` (`src/okf/ops/frontmatter.rs`): removes the entry
  whose `id` matches, the inverse of `ops::source`. Like `unquestion`, it
  removes the item's lines in place in a block list (continuation lines
  included), rewrites a flow list as a block list of the remaining entries,
  and deletes the key when the last entry goes. It refuses an id no entry
  has, and refuses `sources` that is not a list (`OkfError::Shape`).
- It also refuses while a footnote in the body still cites the entry, and
  the message names the footnote:
  `footnote [^x] in a.md still cites source 'id'; remove or rewrite the
  citation first`. A footnote cites an entry when its label is the id
  (referenced or only defined), or its definition, continuation lines
  included, holds the id as a whole token (no letter, digit, `_` or `-`
  either side, so `s1` does not match `s12`), or holds the entry's title or
  resource.
- The `remove_source` MCP tool (`src/mcp/writes.rs`, `path`, `id`,
  `changeset`), in the bookkeeping router beside `add_source`. It runs
  through `apply` like the other bookkeeping writes: it needs write access,
  is stored as a changeset entry with no replay op (a frontmatter edit, so a
  stale base conflicts at publish), and a refusal stores nothing.

## Changed

- `set_frontmatter`'s refusal for a managed key now lists `remove_source`
  among the tools that own those keys.
- README's bookkeeping tool table lists `remove_source`, marked as not in
  `okf.py`.
- The tool counts in `tests/maintenance.rs` and
  `src/investigator/client_tests.rs` go from 40 to 41.

## Why the citation rule differs from `split_concept`'s

`split_concept` picks the sources to carry with a looser rule: a cited
definition that contains the id as a bare substring counts. There, a false
match copies one extra source. Here, it would refuse a removal with no way
round it short of rewriting an unrelated footnote, so the id must match as
a whole token. Title and resource stay substring matches: they are long
enough not to collide by accident.

## Tests

- Unit (`frontmatter.rs`): removing a block item with continuation lines;
  the last entry deleting the key; a flow list rewritten; refusals for a
  cited entry by label, by resource, by id token and by a title on a
  continuation line, each naming the footnote; an uncited neighbour still
  removable; unknown id, no `sources`, scalar `sources`; `contains_token`
  boundaries, multibyte neighbours included.
- Store-backed (`writes.rs`): `remove_source` after two `add_source` calls
  in one changeset leaves only the kept entry and stores no replay op; a
  refused `remove_source` stores nothing.
