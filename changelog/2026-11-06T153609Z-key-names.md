# Key names and immutable credential IDs

Issue #174. API-key names now group credentials while each credential keeps
an immutable generated ID, so a revoked name/actor pair can be reissued
without changing historical ownership.

## Changed

- Migration `0005_key_names.sql` copies every existing ID into `name`, gives
  new credentials UUID IDs, and permits one live credential per `(name,
  actor)` pair.
- `key create` prints the secret on stdout and the generated immutable ID on
  stderr. `revoke`, `grant`, and `ungrant` accept an immutable ID, an
  unambiguous live name, or a name selected with `--actor`.
- `key list` remains tab-separated but its columns are now **name, actor, id,
  access, state, catalogs, default**. This is an intentional incompatible
  change for scripts that parsed the former **id, access, state, catalogs,
  default, actor** order.
- `list_changesets` reports both the key name and immutable ID; historical
  changesets and revisions retain the credential and actor that created them.
- A root `justfile` provides the stable `fmt` and `test` validation recipes.

## Compatibility

Existing secret values and key IDs continue to authenticate. Administrators
should update scripts that parse `key list` and may use the immutable ID shown
by `key create` for unambiguous automation.
