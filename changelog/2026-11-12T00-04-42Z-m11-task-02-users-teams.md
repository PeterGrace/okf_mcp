# M11 Task 2: store::users, store::teams and the test fixture

## Added
- `store::users`: `create` (the user plus its personal team, the user as owner), `list`, `find`, `delete`, and crate-internal `id_of`, `check_name`, `check_free` and `or_name_taken`. Users are addressed by name; ids stay inside SQL. `UserRecord` counts the keys, grants and sign-in codes naming the user and lists its teams.
- `store::teams`: `Role` (`owner`/`member`, with `clap::ValueEnum` and lowercase `serde::Deserialize`), `NewTeam`, `Member`, `TeamRecord`, `MemberChange`, and `create`, `list`, `find`, `set_member`, `remove_member`, `delete`. `list` and `find` use two queries (team rows, then memberships grouped in Rust), never one per team.
- The spec's deletion rules: a user is not deleted while a credential names it, it belongs to another team, or its personal team owns a catalog; a personal team or a team owning a catalog is not deleted; the last owner is not removed or demoted; a personal team's own user is not removed. Each is a 409 (`Refused`); an unknown user or team is a 404 (`UnknownName`). Every write bumps the administrative generation in its transaction.
- Unit-test fixture: `db::test_db()` creates user `test-user` (personal team `test-user`), named by `crate::db::TEST_USER` and `TEST_TEAM`.
- Tests in both modules, including the two name-race tests (`a_name_that_loses_the_insert_race_is_refused_not_a_database_error`, `concurrent_user_and_team_creates_of_one_name_give_one_winner_and_a_409`) and `concurrent_removal_of_two_owners_leaves_one`.
- Deletion-guard tests seeded with SQL against migration 0009's columns (review of #289): a user named by a key or by a sign-in code, a user whose personal team owns a catalog, a team that owns a catalog, and a two-transaction race where a catalog is assigned to the personal team during the user's delete. Each asserts `Refused` and that nothing changed.

## Changed
- `migrations_create_the_schema_and_rerun_as_a_no_op` migrates a bare database instead of `test_db()`, since the fixture user bumps the admin generation it expects at 0.
- Nine `store::catalogs` and `store::keys` tests that asserted an absolute admin generation now read it right after `test_db()` and assert relative to that.

## Notes
- `users::delete` locks the personal team row `FOR UPDATE` before counting its catalogs (review of #289), so a catalog assigned concurrently gives a 409, not a foreign-key database error. The race test fails without the lock.
- Name races: `check_free` only narrows them. Every user and team INSERT maps a unique violation to the same "name taken" 409, so a user and a team created concurrently with one name never surface a database error.
- Last-owner and deletion checks lock the team row `FOR UPDATE`, so concurrent membership changes to one team run one at a time.
- Plan corrections (Task 2 Steps 5 and 7, the shared interfaces, Task 3 Step 3): `teams::id_of` moves to Task 3, its first caller, because `-D warnings` refuses dead code; `lock_team` returns the team's id and personal owner; members are grouped by team name; the fixture-affected tests are named.
