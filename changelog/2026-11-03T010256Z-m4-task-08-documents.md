## Added

- `src/okf/doc.rs`: `Doc::body`, the text after the frontmatter (the whole text without
  one), line endings as written. `from_text` keeps the closing `---` as the tail's first
  line, so `body` skips it when there is frontmatter. One unit test and a doc test.
- `src/mcp/documents.rs`: the `get_concept` tool (`GetConceptParams` -> `Concept`): the
  catalog, path, title, frontmatter as JSON (keys in file order; null and
  `frontmatter_error` when it does not parse) and body; with `links`, the outbound links
  (in-page links left out) with each target's title, description and `broken`, and the
  backlinks with each source's title; with `raw`, the file verbatim. Fields not asked for
  are left out of the JSON. The `read_document` tool (`ReadDocumentParams` ->
  `Document`): the raw text of any folder's `index.md` or `log.md` or the root
  `AGENTS.md` (default `/index.md`); any other path, or one outside the catalog, is
  `InvalidPath`. Four tests.

- The plan: a dated `Corrected (issue #71)` note in Task 8 (more asserts, a fourth test;

## Notes

- Without `catalog`, both tools look through the selected catalogs in order and answer
  from the first that has the path (Decision 1). For `get_concept`, a catalog holding the
  path as a non-concept document does not stop the search; its `InvalidPath` is returned
  only if no later catalog has the concept. A document's kind depends only on its name,
  so a later catalog can answer only through `resolve_concept`'s other spelling
  (`index.md` refused, `index.md.md` found); the read-set test covers it.
- Both tools spell their return type `Result<Json<T>, CallToolResult>`, so rmcp lists them
  with output schemas; `the_server_lists_both_tools_with_object_output_schemas` checks it.
- Neither tool does CPU work worth a blocking thread: per catalog tried, a few hash-map
  lookups in the snapshot, then copying one document and its links and backlinks.
