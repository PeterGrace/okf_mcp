# M3 Task 5: `store::catalogs` and `okf-mcp catalog` (2026-11-02T16:11:43Z)

Issue #41, Task 5 of `docs/superpowers/plans/2026-11-02-okf-mcp-m3-storage.md`. Catalog
rows get their store functions and their subcommand; every change bumps
`server_state.admin_generation` in the same transaction, so a running server (M4)
notices.

## Added

- `src/store/mod.rs`: the store module root (`pub mod catalogs`).
- `src/store/catalogs.rs`: `Catalog` (a `FromRow` struct), `is_valid_name`
  (`[a-z0-9-]+`, as the schema's `CHECK`), `create` (refuses a bad or taken name;
  the duplicate is caught as SQLSTATE 23505), `list` (by name), `find` (generic over
  `PgExecutor`, so it runs on a pool or inside a transaction), `delete` (under the
  catalog lock; refuses while an open changeset holds entries unless `force`; the
  foreign keys cascade to documents, history, changesets and grants), and
  `admin_generation`. Crate-private helpers for later tasks: `lock` (the two-key
  `pg_advisory_xact_lock(CATALOG_LOCK_NAMESPACE, catalog_id)`, namespace `0x006f6b66`,
  "okf"), `bump_admin_generation`, `is_unique_violation`.
- `OkfError::CatalogNotSelected { catalog }` and `OkfError::Refused { reason }`.
- `okf-mcp catalog create <name> [--description D] | list | delete <name> [--force]`.
  `list` prints `name<TAB>generation N<TAB>description` per catalog.
- Tests: `store::catalogs::tests::{create_list_and_find,
  bad_and_duplicate_names_are_refused, delete_refuses_unpublished_work_unless_forced,
  an_empty_open_changeset_does_not_block_delete,
  the_lock_holds_other_transactions_off_until_commit}` and
  `cli::tests::{catalog_subcommands_parse, catalog_create_runs_against_the_database}`.

## Changed

- `src/cli.rs`: `run` uses `clock` (`created_at` comes from `clock.now()`); Task 4's
  `let _ = clock;` is gone. `_config` stays until Task 8.
- `src/lib.rs`: `pub mod store;`.

## Notes

- The code matches the plan's Task 5 signatures. Beyond it: one extra test,
  `the_lock_holds_other_transactions_off_until_commit`, which checks with
  `pg_try_advisory_xact_lock` that a second transaction cannot take a held catalog
  lock and can once the holder commits, and `an_empty_open_changeset_does_not_block_delete`
  also asserts the catalog is gone. Later tasks' calls (`catalogs::{find, lock,
  bump_admin_generation, is_unique_violation, admin_generation, create, delete}`)
  match these signatures; the plan's Task 5 gets a dated "Corrected (issue #41)" note for the extra test and assertion.
- Checked by hand against a throwaway `postgres:17-alpine`: create, a bad name and a
  duplicate (each exits 1 with the reason), list, delete of an unknown catalog (exits
  1), delete, and `okf-mcp catalog --help`.
- Review of PR #55: `delete` re-checks the catalog row `FOR UPDATE` after the advisory
  lock (a delete that waited on a racing one now fails with `CatalogNotSelected`
  instead of bumping the generation and reporting success), and locks the open
  changesets `FOR UPDATE` before the unpublished check, so an entry written
  concurrently is either seen (refused) or fails its foreign-key check, never cascaded
  away without `--force`. `lock` binds the id as `$2::int4`, so an id above `i32::MAX`
  is a database error rather than a panic. Tests
  `a_delete_that_waited_finds_the_catalog_gone`,
  `an_entry_written_during_a_delete_is_refused_not_cascaded` (both fail without the
  fix) and `an_id_beyond_int4_is_a_database_error`.
- `Cargo.toml`: a `[dev-dependencies]` `tokio` entry with `features = ["time"]`, for
  the concurrency tests' `tokio::time::sleep`; before this, `time` reached the tests
  only through another crate's features.
