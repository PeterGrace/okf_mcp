# M6 Task 6, review of PR #134 (2026-11-03T164133Z)

Brooke's nit on PR #134 (issue #125): a blank `type` on `split_concept` was copied
into the new concept's frontmatter.

## Added

- `okf::ops::blank_type()` (crate-private): the refusal for a blank or non-string
  concept `type`, "type must be a non-blank string; every concept needs one".
- Tests: `okf::ops::split::tests::a_blank_type_is_refused_before_anything_is_read_or_written`
  (`""`, `" "`, `"\t\n"`; nothing written) and
  `mcp::restructure::tests::a_blank_type_is_refused_and_nothing_is_stored`.

## Changed

- `split_concept` (the op) refuses a blank `kind` first, with `blank_type()`,
  before it reads anything. `set_frontmatter` uses the same helper instead of its
  own copy of the text.
- `split_concept`'s `type` parameter description and the design's row say a blank
  one is refused.
- Plan Task 6: a dated Corrected note.

## Notes

- This diverges from `okf.py`, whose `split --type ""` writes `type: ""`. The
  divergence is listed in `src/okf/ops/split.rs`'s module doc. The parity script
  never passes a blank type, so the goldens are unchanged.
- The check is in the op, not the tool, so Task 7's direct op calls and the tool
  agree.
