# M5 Task 1: changesets keyed by (catalog, key, label), and the lock order

Issue #90. Plan: `docs/superpowers/plans/2026-11-03-okf-mcp-m5-writes.md`, Task 1
(Decisions 1 and 3).

## Added

- `migrations/0002_changeset_identity.sql`: renames `changesets.session_id` to
  `label`; replaces `changesets_one_open_per_session` with
  `changesets_one_open_per_label` on `(catalog_id, key_id, label) WHERE state = 'open'`;
  adds `version bigint NOT NULL DEFAULT 0`, bumped by every change to a changeset or
  its entries (Task 7's overlay cache keys on it).
- `src/store/changesets.rs`:
  - types: `ChangesetState` (with `as_str`, `parse`), `ChangesetRow`, `EntryRow`
    (`sqlx::FromRow`), `ChangesetKey`, `StrandedRow`, and the `CATALOG_GONE` message;
  - `lock_catalog`: the catalog row `FOR KEY SHARE`, the first lock of every write;
    a row gone (deleted while the write waited) is `Refused` with `CATALOG_GONE`;
  - `find_open`, `by_id`, `entries` (ordered by path);
  - `get_or_create`: `INSERT ... ON CONFLICT DO NOTHING RETURNING`, else the winning
    row read `FOR UPDATE`, so the write holds its changeset's row lock from here on;
    up to three tries, then `Busy`;
  - `upsert_entry` and `remove_entries` (`None` drops every entry): both first bump
    `version` with an `UPDATE ... WHERE state = 'open'` (the changeset row lock, step 2
    of the order), answering `Busy` if the changeset closed meanwhile;
  - `set_state` (open to published or discarded; `Refused` if not open);
  - `stranded` (open, non-empty, idle past a cutoff, with catalog name and sorted
    paths);
  - `adopt` (new key and label; `Refused` when that key and label already have an
    open changeset in the catalog);
  - `prune_empty`: discards empty open changesets idle past a cutoff, without the
    catalog lock, skipping rows other transactions hold (`FOR UPDATE ... SKIP
    LOCKED`), so it never waits.
- `OkfError::Busy { reason }`: HTTP 503, kind `"Busy"`, not internal, message ends
  "retry".
- Tests: the 11 `store::changesets` tests, including the two concurrency tests
  `a_delete_waits_for_a_write_then_refuses_its_work` and
  `a_write_waits_for_a_delete_then_sees_the_catalog_gone` (both await with a 30 s
  `tokio::time::timeout`, so a lock-order regression fails rather than hangs), and
  `http::tests::busy_is_503_and_says_to_retry`.

## Changed

- `Cargo.toml`: sqlx gains the `json` feature (the `replay` jsonb column as
  `serde_json::Value`).
- `src/error.rs`: `Database`'s `#[from]` became `#[source]`; a hand-written
  `From<sqlx::Error>` maps SQLSTATE `40P01` (deadlock) and `40001` (serialization
  failure) to `Busy`, everything else to `Database`, so every `?` gets it.
- `src/app.rs`: `note_failure` treats `Busy` like `Database` (retry at the next poll),
  so a deadlock during a refresh does not mark the generation broken.
- `src/store/catalogs.rs`: `delete` locks the open changesets `ORDER BY id`; its doc
  states the shared lock order instead of the M3 deadlock caveat; the tests use
  `label`.
- `src/db.rs`: `constraints_hold` gives its two open changesets a key (NULL `key_id`s
  never conflict) and asserts `changesets_one_open_per_label`.
- Design (`docs/superpowers/specs/2026-10-26-okf-mcp-server-design.md`): "Decisions"
  (Write grouping), "Storage" (the `changesets` row, the index, a new "Lock order"
  paragraph), "Session lifecycle", "Errors" (`Busy`), "Open questions for M5" (the
  identity question and the M3 deadlock clause removed).
