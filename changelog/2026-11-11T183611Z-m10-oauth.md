# Milestone 10: OAuth 2.1 and directory readiness (epic #244)

OAuth-only MCP clients (ChatGPT and Claude.ai custom connectors, the Claude
and ChatGPT connector directories) can connect through a built-in OAuth 2.1
authorization server, beside the static API keys, which work as before. An
admin-issued single-use sign-in code, entered on the server's consent page,
becomes an OAuth grant: a key row of kind `oauth` with the code's catalogs,
access (never admin) and actor. Every tool carries a title and behaviour
hints. Design: `docs/superpowers/specs/2026-11-11-okf-oauth-design.md`;
plan: `docs/superpowers/plans/2026-11-11-okf-mcp-m10-oauth.md`.

## Added

- **Task 1, tool annotations (#245, PR #253):** a title and `readOnlyHint`,
  `destructiveHint`, `idempotentHint` and `openWorldHint` on all 41 tools,
  and a classification test every new tool must pass.
- **Task 2, foundation (#246, PR #254):** migration `0008_oauth.sql`
  (`api_keys.kind`, `oauth_clients`, `sign_in_codes`, `oauth_tokens`, and
  checks that keep grants below admin); `public_url` and `[oauth]`; the
  `BearerVerifier` trait with prefix dispatch (`okf_` keys, `okfat_` access
  tokens) and the audience check; `resource_metadata` on every 401; the
  `src/oauth/` skeleton (bounded expiring maps, token-bucket rate limits,
  `OAuthError`); hourly cleanup in the poll loop.
- **Task 3, metadata and clients (#247, PR #257):** Protected Resource
  Metadata (RFC 9728) and authorization server metadata (RFC 8414); dynamic
  client registration (RFC 7591) with a cap that holds under concurrency;
  the hardened Client ID Metadata Document fetcher and its cache.
- **Task 4, sign-in codes (#248, PR #255):** the sign-in code store,
  `okf-mcp oauth code create|list|revoke` and `oauth grant list|revoke`, and
  the `/api/v1/oauth/codes` endpoints. `okf-mcp key ...` resolves API keys
  only.
- **Task 5, authorize and consent (#249, PR #259):** `/oauth/authorize` with
  exact redirect matching, required S256 PKCE and the resource check; the
  two-step consent page (code, then what will be granted), with CSRF
  protection, a per-summary nonce and a CSP whose `form-action` admits the
  validated redirect; redemption in one transaction.
- **Task 6, tokens (#250, PR #262):** `/oauth/token` (authorization code and
  rotating refresh tokens with reuse detection, serialized per family) and
  `/oauth/revoke` (RFC 7009); end-to-end tests of the whole flow with CIMD
  and with DCR, beside a static key.
- **Task 7, console (#251, PR #256):** the "Sign-in codes" panel on the API
  keys page, and OAuth grants marked in the key list with their client.
- **Task 8, documentation (#252, PR #263):** "OAuth connectors" in
  `docs/operations.md`, the configuration reference, the 0.13.0 upgrade
  note, troubleshooting rows, the README, and the spec's wrap-up.

## Changed

- A 401 carries `WWW-Authenticate: Bearer resource_metadata="..."` when
  OAuth is on. Without `public_url` it is unchanged.
- `require_key` admits OAuth access tokens as well as API keys.
- `/api/v1/whoami` and the key list show a credential's `kind` and
  `client_name`.
- The live name/actor uniqueness rule covers API keys only.

## Notes

- Without `public_url` the server behaves as 0.12.1 apart from the
  migration and the tool annotations.
- The server stays single-replica. Pending consent pages and authorization
  codes are in memory, so a restart interrupts at most a sign-in in
  progress.
- Clients that use Client ID Metadata Documents need the server to reach
  their host over HTTPS directly (the fetcher ignores proxy variables).
- The release (v0.13.0, `just release-prepare minor`) is the second part of
  issue #252, on `main` after the maintainer's go-ahead.
