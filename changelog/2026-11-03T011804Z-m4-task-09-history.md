  newest `limit` rows of `revisions` (`RevisionRow`: revision, op, actor, message,
  created_at; content left out), read backwards along the primary key. Test
  `revisions_come_newest_first_and_outlive_a_delete`.
- `src/mcp/history.rs`: the `history` tool, `HistoryParams` (`path`, `catalog`,
  `limit`), `Revision` and `History` (`catalog`, `/`-prefixed `path`, `revisions`
  newest first, times as `2026-11-02T21:00:00Z`). Without `catalog`, the first catalog
  of the read set with any revision of the path answers (Decision 1). Paths are spelled
  as for `get_concept` (leading `/` and `.md` optional), but any file has a history, a
  deleted one included. Tests: `the_limit_defaults_to_20_counts_0_as_1_and_is_capped_at_200`,
  `candidates_add_md_and_drop_paths_that_leave_the_catalog`,
  `the_server_lists_history_with_an_object_output_schema` and

## Notes

- `limit` is capped at 200, as `search`'s is: a long-lived `log.md` gains a revision per
  import and publish, and one response should stay a reasonable size for an MCP client.
  0 counts as 1, so a zero limit never makes a path look as if it had no history.
- Each lookup is one indexed query per (catalog, candidate path), stopping at the first
  hit, so the cost is at most 2 x catalogs queries of at most `limit` rows each.
- M3's import records `import` for every added or changed file and `delete` (message
  `import`) for one it drops; the store test covers both.
